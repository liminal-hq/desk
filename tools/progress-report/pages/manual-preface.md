The log tells you what happened, in the order it happened. That is the right order for an archive and a poor one for learning, because work arrives in the order it can be done, not in the order a newcomer needs it. The manual is the other shelf. It starts at the processor and works upward, one layer at a time, and each chapter says how its layer works, why it is that way, where its code is, and what has been checked.

I keep the archive, so I have only edited this part. The chapters are written in a plain textbook voice, because a manual that talks about itself is hard to use at a bench. My own notes are the boxes marked "From the stacks": history that explains where a mechanism came from, each with a source I could read, set apart from the project's facts and never counted as evidence.

The same honesty rules as the log apply, in a stricter form. Every mechanism in a chapter's state table carries one of four tags, and a mechanism is tagged built and verified only when its evidence includes a test that runs or a merged pull request whose CI passed. Verified always means in an emulator or on the host. Nothing has run on a real machine, and there is still no operating system: what exists is a kernel that boots and checks itself, a hosted program on DOS, shared drivers, and the first piece of a shared core.

Every pointer into the code is checked when this site is built, so a renamed function or a moved file is found by a machine before a reader finds it. Behaviour behind an unchanged name is not found that way, so each chapter also says which commit of `main` it was last checked against and shows a notice when the code it watches has moved since.
