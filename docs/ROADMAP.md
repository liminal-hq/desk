## Path to the first OS milestone

The first OS milestone is: the native kernel boots, opens a window, and runs a separate program loaded from disk (R80). Until that works the native track is a kernel with a shell inside it, not an operating system. The order below is the owner's; each step names its items.

1. Finish and verify live input (R47): done. The stack is merged, and `tools/check.sh` passed from a clean clone of `main` in the CI image on 2026-11-11 (emulators only, nothing on real hardware).
2. The module loader spike: an executable format and loaders for both tracks (R48), which is the next step; its design and build plan are written ([`LOADER.md`](LOADER.md), [`LOADER-PLAN.md`](LOADER-PLAN.md)) and nothing is built.
3. Decide the path and mount model and the shared commands (R125, R126), which are proposals, so the filesystem and the app model are written against them.
4. A floppy or IDE driver and a read-only FAT filesystem (R74, R75; spike R50).
5. Tasks, preemption, threads and a system-call boundary between the kernel and apps (R77, R141, R142; [`APP-MODEL.md`](APP-MODEL.md)).
6. The first separate app running from disk (R76, R79, R80).

Paging and per-task address spaces (R51, R78), sound and timing for Fizz (R81), DOS programs under the kernel (R49) and real hardware (R64) follow or run beside this path; none of them blocks it. The full shell and apps (R84 to R124) come after the milestone: they need the app model (R79) and, for most apps, the filesystem (R75), but the shell parts that need neither (the widgets, menus, bar and window operations) can be built on the first window's core in parallel.

## How to read it

Each item has an id (R1, R2 and so on, never reused), a title, a status, the outcome in one line and the evidence: pull requests (`#NN`), documents and commits.

| Status | Meaning |
|---|---|
| `done` | Merged into `main`. The outcome says what was verified and how, and what was not |
| `in progress` | Started, with part of the outcome met or its checks still open. The entry says what is merged and what is not, or names the open pull request |
| `planned` | Decided, in a known order, not started |
| `idea` | Mentioned in a document or by the owner; not decided and not ordered |
| `blocked` | Cannot proceed until something outside the work happens |

Items R84 to R140 are read slightly differently. Their status follows the inventory of what [`SHELL-DESIGN.md`](SHELL-DESIGN.md#what-is-built) found built: a part with no code is `planned`, a part with some merged code is `in progress` and says which half is merged, and nothing is `done` until it is merged and evidenced. "Depends on" names items (R79 is the app model, R75 the filesystem). A design item says it is a decision for the owner, and a finding says its evidence is the owner's run, not a check.

Three limits apply to every `done` item unless it says otherwise. No code has run on a real 486, a real floppy drive, a real VGA card or a real mouse; "verified" means on the host, in DOSBox Staging, in QEMU (as a 486) or, where stated, in Bochs and 86Box. The emulators model the hardware and are not the hardware. And the design documents were written before the code, so where a document and the code disagree the code wins (see R55).

## Reuse and vendoring

Nothing is vendored, and nothing here has been checked for compatibility. The project's licence is Apache-2.0 OR MIT; for each candidate the first thing to check is its licence and whether it is compatible with that dual licence, and every candidate below is **to be assessed**. A decision to vendor or depend on outside code needs the owner, a `NOTICE` entry (`NOTICE` already lists third-party material), and, where the code would be in `shell/`, a change to the rule in `AGENTS.md` that `shell/` takes no external crates. That rule is the project's own and can be adapted. It is scoped to the `shell/` core, which has to stay deterministic and buildable for 486 targets; a kernel-side driver or filesystem could take a vetted, vendored and pinned crate, recorded in `NOTICE` and kept behind the HAL, once the owner decides. The adaptation would be its own small documentation pull request, editing `AGENTS.md` and `CLAUDE.md`, made before any code is vendored.

## How to keep this current

- **Who.** The agent that lands a change updates this file in the same pull request; the owner reviews it with the change. A pull request that completes, starts or abandons an item says so here.
- **When.** At least when a pull request merges, when a spike starts, and when a result document says something this file claims otherwise. A fresh read against `gh pr list --state all` before each release or progress-report publication catches drift.
- **Status changes need evidence.** Every change of status cites a pull request number (`#NN`), a document or a commit, and a `done` item states what was verified and how, and what was not. An item never goes to `done` before its pull request is merged into `main`.
- **Ids are stable.** New items take the next number; a dropped item stays with the status `idea` and a note on why, instead of being deleted.
- **Check it.** Run `python3 -I tools/check-docs.py` before committing.
